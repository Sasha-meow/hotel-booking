# Hotel Booking System

Микросервисная система для бронирования отелей с поддержкой распределенных транзакций (Saga) и JWT-авторизации

### Основной функционал
- Регистрация и аутентификация пользователей (JWT)
- Разграничение ролей: ADMIN/USER
- Управление отелями и номерами (CRUD)
- Алгоритм планирования занятости номеров (сортировка по `times_booked`)
- Двухшаговая согласованность (Saga) с компенсацией при сбое
- Идемпотентность запросов (через `Idempotency-Key`)
- Блокировка пересекающихся дат (`Pessimistic Write`)

## Запуск проекта

> **⚠️ Внимание!** Проект состоит из 4 независимых сервисов. Их нужно запускать строго в указанном порядке.

### 1. Сборка проекта
В корневой папке выполните:
```bash
mvn clean install -DskipTests
```

*(Эта команда соберет все модули, включая common-lib, и установит их в локальный репозиторий Maven).*

> **💡 Если Вы пользуетесь Intellij IDEA** - после клонирования проекта обязательно нажмите Load Maven Changes, чтобы IDEA подхватила модуль common-lib.

### 2. Запуск сервисов (в порядке важности)

1. **Eureka Server** (порт 8761) - `eureka-server`
2. **Hotel Service** (порт 8081) - `hotel-service`
3. **Booking Service** (порт 8082) - `booking-service`
4. **API Gateway** (порт 8080) - `api-gateway`

*(Все сервисы можно запустить из IntelliJ IDEA, открыв их главные классы и нажав Run).*

### 3. Проверка работоспособности

Откройте в браузере сваггеры сервисов:
```text
http://localhost:8081/swagger-ui.html
http://localhost:8082/swagger-ui.html
```

Если нужно через Gateway на данный момент есть два пути (общего Swagger пока нет):
1. Postman
2. Для Intellij IDEA в корне проекта есть [файл с запросами](test-example.http), которые можно запустить прямо в IDE.

## Краткая схема работы

```text
Клиент
  │ (JWT)
  ▼
API Gateway :8080 (маршрутизация)
  │
  ├── /api/hotels/** ───► Hotel Service :8081
  │                       - RoomRepository (Pessimistic Lock)
  │                       - RoomBlock (даты)
  │                       - release() ◄───────────────┐
  │                                                   │
  └── /api/bookings/** ──► Booking Service :8082      │
                          - Создает бронь (PENDING)   │
                          - Вызывает Hotel (Feign)    │
                          - RetryService (3 попытки)  │
                          - Меняет статус             │
                          - При сбое: Feign ──────────┘

Все сервисы регистрируются в Eureka Server :8761 (Service Discovery)

```

1. Клиент аутентифицируется и отправляет запрос через **API Gateway**, который маршрутизирует его в нужный сервис.
2. **Hotel Service** управляет номерами и использует `Pessimistic Lock` для защиты от одновременного бронирования одних и тех же дат.
3. **Booking Service** создает локальную бронь (`PENDING`) и через **Feign** запрашивает подтверждение у Hotel Service.
4. При успехе бронь переходит в `CONFIRMED`. При сбое срабатывает **Retry** (3 попытки), а затем компенсация: Booking Service вызывает `release` в Hotel Service, чтобы освободить номер, и бронь отменяется (`CANCELLED`).
5. Все сервисы автоматически находят друг друга через **Eureka Server**.

## Архитектурные решения (ADR)

### 1. Использование пессимистичных блокировок (Pessimistic Lock)
**Контекст:** При бронировании номера два пользователя могут одновременно отправить запрос на пересекающиеся даты. Без блокировок оба запроса могут пройти проверку, что приведет к дублированию броней.
**Решение:** В Hotel Service используется `@Lock(LockModeType.PESSIMISTIC_WRITE)` в методе `RoomRepository.findByIdForUpdate()`. Это блокирует строку номера в БД на время транзакции, заставляя второй запрос ждать завершения первого. 

**Последствия:**
* Плюсы: 100% гарантия отсутствия гонок данных (race conditions).
* Минусы: Небольшое снижение производительности при высокой нагрузке (запросы выстраиваются в очередь).

### 2. Паттерн Saga для распределенных транзакций
**Контекст:** Создание бронирования включает два независимых сервиса (Booking и Hotel). Использование глобальных транзакций (2PC) избыточно и сложно в поддержке.
**Решение:** Реализован паттерн Saga. Booking Service создает бронь в статусе `PENDING`, затем вызывает Hotel Service. При успехе бронь переходит в `CONFIRMED`. При сбое (тайм-аут, ошибка 5xx) выполняется компенсация: бронь переходит в `CANCELLED`, а в Hotel Service отправляется запрос `release` для освобождения дат. 

**Последствия:**
* Плюсы: Сервисы остаются слабо связанными, нет единой точки отказа (как при 2PC).
* Минусы: Требуется реализация механизмов Retry и компенсации (через `RetryService`).

### 3. Идемпотентность через `Idempotency-Key`
**Контекст:** Сетевые сбои могут привести к повторной отправке одного и того же запроса клиентом (например, при тайм-ауте).
**Решение:** В Booking Service добавлена проверка заголовка `Idempotency-Key`. Если запрос с таким ключом уже обрабатывался (есть в БД), возвращается существующая бронь без создания новой. 

**Последствия:**
* Плюсы: Защита от случайных дублей.
* Минусы: Требуется дополнительное хранение ключей в БД (сейчас используется поле `request_id` в таблице броней).

### 4. Вынос общего кода в модуль common-lib
**Контекст:** DTO (например, AvailabilityRequest), константы и глобальные обработчики ошибок дублировались в обоих сервисах.
**Решение:** Создан отдельный Maven-модуль common-lib, который подключается как зависимость к Booking и Hotel. Это устранило дублирование (принцип DRY). 

**Последствия:**
* Плюсы: единый контракт для сервисов.
* Минусы: при изменении общего DTO нужно пересобирать оба сервиса.
